## 一、F1：外部 MCP 执行入口（真实 facade → 窄桥 → bwrap）

探针在 `sandbox-mcp` 容器内用镜像自带的 MCP SDK，以 `SANDBOX_MCP_TOKEN` 连
`http://127.0.0.1:8082/mcp`，调用 `sandbox_shell_execute` / `sandbox_python_execute`。
本栈 exec 的实际配置（`.env` 覆盖了 Compose 默认值）：`SANDBOX_MAX_PROCESS_COUNT=40`、
`MAX_OPEN_FILES=256`、`MAX_CPU_TIME_SECONDS=900`、`MAX_FILE_SIZE_MB=512`、
`EXECUTION_TIMEOUT_SECONDS=600`。**9 / 9 通过**：

| 断言 | 结果 |
|---|---|
| `F1_mcp_shell_rlimits` | 沙箱内 `u=40 n=256 t=900 f=524288 v=unlimited`，与 exec 配置逐项一致（修复前该入口不下发任何 rlimit） |
| `F1_mcp_nproc_denies_descendants` | 有界起 60 个 `sleep 2`：`bash: fork: retry: Resource temporarily unavailable` |
| `F1_mcp_nproc_allows_within_limit` | 正对照：5 个并发作业 `FIVE_JOBS_OK`，无 fork 错误 |
| `F1_mcp_python_rlimits` | Python 入口 `RLIMIT_NPROC=40`、`RLIMIT_NOFILE=256` |
| `F1_mcp_timeout_over_budget_rejected` | `timeout_seconds=301` → `timeout_seconds exceeds MCP limit`，命令未执行 |
| `F1_mcp_timeout_in_budget_ok` | 正对照：`timeout_seconds=300` 成功 |
| `bridge_context_ensure` | 窄桥直连 200 |
| `F1_bridge_disconnect_stops_command` | `sleep 6; echo LATE > late.txt`，2 秒时客户端断开；8 秒后 `test -e late.txt` → `ABSENT`；`ps` 无残留 `sleep 6` |
| `F1_bridge_no_disconnect_control_writes` | 正对照：不断开的 `sleep 1; echo ON_TIME > ontime.txt` 写入成功 |

**未在真机覆盖**：本栈执行预算 600 秒大于桥自身上限 300 秒，「按
`SANDBOX_EXECUTION_TIMEOUT_SECONDS` 收紧桥上限」这一分支在此配置下测不到，由
`exec/test/internal-mcp-limits.test.ts` 的生产工厂用例（`createExecAppFromEnv`，
预算 45 秒 → 46 秒 400）覆盖。配额准入 / 执行中超额终止走与内部路由同一份
`runGuardedForeground`，真机只在上一轮证据中对内部路由做过，本次未另起低阈值容器重跑。
facade 与外部 MCP 客户端之间的断开是否会取消桥请求，不在本次范围。

## 二、F3：真实 MySQL 账本上的缩深闸门

| 步骤 | 结果 |
|---|---|
| 基线 | 账本无非终态 Run；`{bull}:agent-runs-d1/d2` 的 wait/paused/active/delayed/prioritized 全为 0 |
| 插入探针子 Run | 复制一条既有 Run 的归属字段，`run_id=01KF3DRAINGATEPROBE0000001`、`status=WAITING_APPROVAL`、`subagent_depth=2`、`parent_run_id` 指向原 Run |
| `AGENT_SUBAGENT_MAX_DEPTH=1` 启动 Worker | **拒启**：`refusing to start: non-terminal runs deeper than AGENT_SUBAGENT_MAX_DEPTH=1 still exist in MySQL: depth 2=1 …`。Redis 队列为空——修复前的闸门会放行 |
| 探针 Run 改为 `CANCELLED` 后同配置重启 | **放行**：`BullMQ consumers started budget=4 d0:agent-runsx3 d1:agent-runs-d1x1 recovery=ok` |
| 清理 | 删除探针行（确认 0 行残留）；默认配置重启，`d0x2 d1x1 d2x1` |

「审批完成」在这里用改状态模拟（让 Run 到达终态），没有走真实审批恢复链路。

**F2 未在真机注入故障**：Worker 在闸门之前已由 `container.start` 连通 Redis，
开发栈上没有低成本的方式只让闸门那几次读取失败。由
`agent/tests/bootstrap/worker-drain-gate.unit.test.js` 经 `startWorkerMain` 覆盖
（读异常 / 不认识的 key 类型 / 查库失败均拒启，且消费者、恢复扫描、outbox 均未启动）。
